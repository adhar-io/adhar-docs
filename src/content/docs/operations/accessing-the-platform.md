# Accessing the Platform

Every Adhar service — Console, ArgoCD, Gitea, Keycloak, Harbor — is reached the same way: **one hostname per service, derived from one base domain, served by one Gateway holding one certificate**. Nothing in the stack hardcodes a host, a port or a cloud; `adhar up` records the edge configuration on the `AdharPlatform` resource and everything else renders from it. This page explains how those layers fit together, how to test each one on its own, and what to do when one of them is down.

## At a glance

| | |
|---|---|
| **URLs** | `https://<service>.<defaultHost>` (cloud, port 443) · `https://<service>.adhar.localtest.me:8443` (local Kind) |
| **Edge** | One Cilium Gateway, `adhar-gateway` in `adhar-system`, GatewayClass `adhar` |
| **TLS** | Terminates at the Gateway, from `Secret/adhar-cert` |
| **kubeconfig** | `~/.adhar/clusters/<cluster>/kubeconfig` (mode `0600`), merged as context `adhar-<cluster>` |
| **Credentials** | `adhar get secrets [-p <package>]` — never scrape pods |
| **Console login** | Keycloak SSO, realm `adhar` (no pasted secrets) |
| **DNS / TLS automation** | external-dns publishes records; cert-manager issues the wildcard via DNS-01 |
| **Fallback** | `kubectl port-forward` while DNS or a certificate is still settling |

## The request path

Understanding this chain is what makes the failures readable — each arrow is a layer you can test on its own.

```text
   client (browser, curl, kubectl)
     │  1. resolve  console.<defaultHost>
     │     cloud : external-dns published an A record -> Gateway LB IP
     │     local : *.localtest.me is public DNS -> 127.0.0.1
     ▼
   edge address
     │  2. cloud : cloud LoadBalancer on :443
     │     local : Docker host port :8443 -> node port 30443
     ▼
   Service/cilium-gateway-adhar-gateway     (adhar-system)
     │  3. generated by Cilium for Gateway/adhar-gateway
     │     cloud : type LoadBalancer      local : type NodePort
     ▼
   Gateway/adhar-gateway   <- TLS terminates here
     │  4. HTTPS listener presents Secret/adhar-cert
     │     cloud : cert-manager wildcard *.<defaultHost> (DNS-01)
     │     local : self-signed platform certificate
     ▼
   HTTPRoute  (hostnames: ["console.<defaultHost>"])
     │  5. parentRefs -> adhar-gateway; shipped by the package itself
     ▼
   Service/adhar-console  ->  pods
```

Two consequences worth internalising. First, **TLS is a Gateway concern, not an application concern** — backends serve plain HTTP inside the cluster, so a certificate problem never looks like an application problem. Second, **a service is reachable only if its package ships an `HTTPRoute`**; a healthy pod with no route has no URL.

In-cluster clients take the same path. On Kind, CoreDNS rewrites `*.adhar.localtest.me` to `cilium-gateway-adhar-gateway.adhar-system.svc.cluster.local`, so ArgoCD performing OIDC discovery against the Keycloak issuer uses the identical FQDN a browser does. That is also why the local Gateway carries a third listener on `:8443`: externally the host's 8443 maps to the 443 node port, but in-cluster callers connect to the Service on 8443 directly.

## Local Kind versus cloud

| | Local (Kind) | Cloud / on-prem |
|---|---|---|
| Base domain | `adhar.localtest.me` (public DNS → 127.0.0.1) | `globalSettings.defaultHost`, a zone you delegate |
| Reaching the edge | Host port `8443` → node port `30443` | Cloud LoadBalancer on 443 |
| Gateway Service | `NodePort`, ports pinned to 30080/30443 | `LoadBalancer` with an external address |
| Certificate | Self-signed; browser warning is expected | Let's Encrypt wildcard `*.<defaultHost>` via DNS-01 |
| DNS setup | None required, and none possible | Delegate the zone **before** `adhar up` |

`adhar up --port 9443` moves the HTTPS host port; the HTTP port derives as *port − 363* (so `9080`). If the port you ask for is already in use, the Kind provider picks the next free one and reports it — so check the output rather than assuming 8443.

## Your domain drives every URL

Set the base domain once:

```yaml
globalSettings:
  defaultHost: platform.example.com
  defaultHttpsPort: 443
  email: admin@platform.example.com
```

| Service | URL |
|---|---|
| Console | `https://console.<defaultHost>` |
| ArgoCD | `https://argocd.<defaultHost>` |
| Gitea | `https://gitea.<defaultHost>` |
| Keycloak | `https://keycloak.<defaultHost>` |
| OpenBao (secrets) | `https://openbao.<defaultHost>` |
| Harbor | `https://harbor.<defaultHost>` |
| Nexus | `https://nexus.<defaultHost>` |

Because the port is standard on cloud, OIDC issuer URLs such as `https://keycloak.<defaultHost>/realms/adhar` match exactly — no port suffix to keep in step.

## kubeconfig is set up for you

`adhar up` writes the cluster's kubeconfig to `~/.adhar/clusters/<cluster>/kubeconfig` (mode `0600`) and merges the cluster, user and context into `~/.kube/config` as `adhar-<cluster>`, making it current. Re-running `adhar up` for the same cluster **replaces** those entries rather than duplicating them.

```bash
kubectl config current-context      # adhar-dev
kubectl get nodes

# or use the standalone file (scripts, CI, another shell):
export KUBECONFIG=~/.adhar/clusters/dev/kubeconfig
```

Every `adhar` command resolves its cluster the standard way: `--kubeconfig`, then `$KUBECONFIG`, then `~/.kube/config`.

## Getting credentials

Never scrape secrets from pods or YAML. The CLI reads the platform's labelled credential secrets from whichever cluster your kubeconfig points at:

```bash
adhar get secrets                 # the credentials needed to sign in
adhar get secrets -p argocd       # one package (the ArgoCD admin login)
adhar get secrets -p gitea
adhar get secrets -p keycloak
adhar get secrets --all           # every credential in the cluster
```

Packages that keep their own login publish a Secret labelled `adhar.io/cli-secret=true` with `adhar.io/package-name=<package>`, so `-p <package>` works for them with no per-app code in the CLI.

The **Console** uses Keycloak SSO — sign in at `https://console.<defaultHost>` with your Keycloak user rather than pasting a secret. In production, rotate the day-0 `gitea_admin` and ArgoCD `admin` passwords by enabling the `credential-rotation` package; it writes break-glass copies to the secrets backend at `secret/adhar/bootstrap-credentials`.

**The secrets backend is OpenBao** (`security/openbao`); the `vault` package ships disabled and exactly one may be on. OpenBao is API-compatible, so nothing changed for consumers: the External Secrets provider is still `vault:`, the `ClusterSecretStore` is still named `vault`, and the in-cluster address is still `vault.adhar-system.svc.cluster.local:8200`.

## DNS and TLS are automatic

| Piece | Behaviour |
|---|---|
| **DNS provider** | Derived from the environment's cloud; override with `globalSettings.dnsProvider` (`cloudflare` for on-prem, `none` to disable). The zone must be `<defaultHost>`, delegated to that provider |
| **Credentials** | Materialised by the CLI into the `adhar-dns-provider` Secret in `adhar-system` — never written to Git |
| **external-dns** | Runs with `--domain-filter=<defaultHost>` and a per-cluster TXT owner id, publishing a record per platform HTTPRoute hostname pointing at the Gateway LB address |
| **cert-manager** | Issues `*.<defaultHost>` through the DNS-01 `adhar-letsencrypt-dns` ClusterIssuer into `Secret/adhar-cert`; without a DNS-01-capable provider the Gateway keeps `adhar-selfsigned` |

> On AWS the Route 53 solver **requires a region**. Without one the ACME challenge sits pending forever, no `_acme-challenge` TXT record is written, and every URL fails TLS while DNS, the load balancer and the Gateway all look healthy. Temporary credentials (SSO, assumed role) work until they expire, then certificate renewal stops silently — use a long-lived key for the platform's DNS identity.

## Verify each layer independently

Work down the request path. The first command that fails names the layer to fix.

```bash
kubectl config current-context                       # 0. right cluster
adhar get status                                     # 1. platform + package health

kubectl get gateway -n adhar-system adhar-gateway \
  -o custom-columns=NAME:.metadata.name,PROGRAMMED:'.status.conditions[?(@.type=="Programmed")].status'
                                                     # 2. want PROGRAMMED=True

kubectl get svc -n adhar-system cilium-gateway-adhar-gateway
                                                     # 3. cloud: LoadBalancer + ADDRESS
                                                     #    local: NodePort 30080/30443

dig +short console.<defaultHost>                     # 4. resolves to that address
kubectl -n adhar-system get secret adhar-cert        # 5. the certificate exists
kubectl get httproute -A | grep console              # 6. a route claims the hostname
curl -sI https://console.<defaultHost> | head -1     # 7. HTTP/2 200

# Crossplane can actually provision (adhar get status does NOT check this):
kubectl get clusterproviderconfigs.kubernetes.m.crossplane.io
```

Then sign in to ArgoCD **through Keycloak**, not as the local admin, and confirm you see the full application list — an empty list after a successful SSO login is an RBAC defect, not a missing cluster.

## The debugging ladder

Climb it in order; each rung removes one layer from the picture.

1. **Is anything serving?** `curl -sk -o /dev/null -w 'HTTP %{http_code}\n' https://<svc>.<host>`. `000` means the socket opened but nothing answered — the Gateway is not Programmed. A TLS error means the Gateway is fine and the certificate is not.
2. **Bypass DNS, keep the edge.** `curl -k --resolve <svc>.<host>:443:<LB-IP> https://<svc>.<host>` sends the right SNI and Host to the right address. If this works, the problem is DNS only.
3. **Bypass the edge, keep the Service.** Port-forward the backend and hit it directly. If this works, the problem is Gateway, route or certificate — not the application.

   ```bash
   kubectl port-forward -n adhar-system svc/argo-cd-argocd-server 8443:443
   # https://localhost:8443
   kubectl port-forward -n adhar-system svc/adhar-console 3000:3000
   # http://localhost:3000
   ```

4. **Bypass the Service, keep the pod.** `kubectl port-forward -n adhar-system pod/<pod> <port>:<port>`. Working here but not at step 3 means the Service selector or endpoints are wrong.
5. **Read the pod.** `kubectl -n adhar-system logs <pod>` and `kubectl -n adhar-system describe pod <pod>`.

To remove the local browser warning entirely, trust the platform CA:

```bash
kubectl -n adhar-system get secret adhar-cert \
  -o jsonpath='{.data.ca\.crt}' | base64 -d > adhar-ca.crt
```

## Common pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| `HTTP 000` on every URL | Gateway never Programmed | Re-run `adhar up`; see [Troubleshooting](/docs/reference/troubleshooting) |
| Browser TLS warning locally | Self-signed platform certificate, by design | Trust the CA, or ignore it |
| `adhar cluster list` says "No clusters found" | It queries nothing without `--file` | `adhar cluster list --file config.yaml` |
| `-f` deleted a cluster without asking | On `cluster delete`, `-f` is `--force`, not `--file` | Always spell out `--file` on delete |
| `adhar up -f config.yaml` built everything | Without `--env`, **every** environment in the file is provisioned | Always pass `--env <name>` |
| DNS resolves, TLS fails | No DNS-01 provider, or an expired cloud credential | Check `adhar-dns-provider` and the cert-manager logs |
